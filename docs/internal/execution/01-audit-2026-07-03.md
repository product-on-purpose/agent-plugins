# Program Audit - 2026-07-03

This is the committed record of the 2026-07-03 program audit of the product-on-purpose standards program. It documents what a nine-pass multi-agent audit found on disk, in CI, and in session history across the marketplace repo and its four family plugins, on the day this execution suite was opened. It backs the rest of the suite at `docs/internal/execution/`; it does not restate or re-derive the standards-plan-roadmap package's decision rationale or clause text. For that, see [`../standards-plan-roadmap/03-decisions.md`](../standards-plan-roadmap/03-decisions.md) (the 17 locked decisions) and [`../standards-plan-roadmap/02-roadmap.md`](../standards-plan-roadmap/02-roadmap.md) (the six-phase roadmap), linked throughout below.

## Scope and method

Eight sub-audits ran in parallel, each scoped to one slice of the program, covering an estimated 1.2 million tokens of source material combined; a ninth pass synthesized their findings into the six sections below. The eight scopes:

1. The standards-plan-roadmap package itself: the 17 locked decisions, the six-phase roadmap, the tier spine, and the open-questions register.
2. The Phase 0 implementation plans: the change manifest and the task-level relocation plan, cross-checked against live repo state.
3. The staged drafts and confirming spikes: nine drafts and two spikes under `drafts/` and `spikes/`.
4. This repo's own mechanics: CI, the registry validator, governance, the `standards/` tree, the `_LOCAL/`/`_agent-context/` state, and live GitHub branch-protection settings.
5. The program and convergence documentation: the older `program-roadmap.md`, the fleet-orchestration program, the convergence audit packets, and the one committed prior audit.
6. This repo's own session logs and gitignored planning notes under `_agent-context/` and `_LOCAL/`.
7. The four family repos (`agent-skills-toolkit`, `pm-skills`, `thinking-framework-skills`, `writing-style-catalog`), audited directly against the live marketplace registry.
8. Claude Code project memory and session transcripts across all six related project directories.

Home repo: `E:/Projects/product-on-purpose/agent-plugins`. Where sources conflicted, this record follows live repo files over audit prose or memory, and flags the conflict explicitly rather than silently picking a side.

The audit's headline conclusion, reached independently by multiple sub-reports: the family is roughly 70 percent built. A versioned Standard, a 30-check conformance runner, a governance and amendment lifecycle, a thin listing contract, a graduated site domain, an orchestration model, and four written convergence-audit packets already exist. What remains is formalization, consolidating duplicated machinery, and bringing two version-pin laggards into governance. This is alignment and convergence work, not a rescue.

### The Codex workstream, in detail

D17 (Codex: deliver) reverses an earlier interim position, the pre-D17 stance that "codex" meant portability via agentskills.io skills, not native marketplace packaging, and commits the family to shipping codex-distributed native packaging for skills and MCP only, explicitly excluding subagents, output styles, and statusline, none of which Codex's own plugin manifest supports as a plugin-shipped surface. The path-reconfirmation spike has already run and reports CONFIRMED-WITH-CAVEATS: discovery is `.agents/skills/` (there is no `.codex/skills/` variant), the native plugin manifest is `.codex-plugin/plugin.json`, and the marketplace manifest is `.agents/plugins/marketplace.json` with a confirmed per-entry schema of `{name, source, policy, category}`. Residual caveats flagged as "verify at build, not blocking": the plugin install verb is app or TUI-driven, not a confirmed CLI command; the plugin manifest's optional `interface` object's required-versus-cosmetic fields need confirming at build time; and the exact `.mcp.json` accepted shape needs pinning at build time. A naming hazard runs through all of this and should be watched in every downstream doc: "OpenAI Codex CLI," the distribution target, is a different thing from the `codex` Claude Code plugin, the consumer-side `codex:*` skills already in use in this repo.

### Phase 0 in detail: the three sequenced PRs

Phase 0 (truth and relocation) is the only phase with an executable, task-level implementation plan. It sequences strictly as three pull requests, and its single most emphasized invariant is: never delete askit's `STANDARD.md`/`scripts/` until its caller is green (the no-dark-window invariant).

1. **PR-A (ship the org gate)**, in `product-on-purpose/.github`: creates and tags `.github/workflows/standards-gate.yml` as a reusable `workflow_call` workflow at `v1.0.0`. It cannot run green until PR-B relocates the runner, so this step only ships and tags it.
2. **PR-B (agent-plugins atomic LAND)**, one pull request per `GOVERNANCE.md` Section 5: relocates `check.mjs`/`tier-report.mjs`/`lib/`/`checks/`/`generators/` and their tests into `standards/checks/`, relocates `STANDARD.md` verbatim (header stays 0.12), creates `standards/CHANGELOG.md` and `RELEASE-NOTES.md`, drops the README "not here yet" caveats, adds the relocation ADR (the plan estimates it as 0002, but per the allocation-at-land invariant this number is not reserved and must be re-verified against the protected head at merge), and sweeps stale 0.8 references and the `writing-style-library`/`writing-style-catalog` name drift.
3. **PR-C (askit RE-ADOPT)**, in `agent-skills-toolkit`, on a separate cadence following PR-B: repoints askit's CI, release, and local-dev to call the reusable workflow, verifies green, and only then deletes askit's now-duplicate copies.

The plan itself names three open sign-off points an executor cannot resolve alone: (1) the version-bump ruling, whose stated default is structural ADR-only with no bump, keeping 0.13 free for the U13 (skill-registration check) warn-to-error burndown; (2) the npm-`check` resolution mechanism for askit's re-adoption, recommending a pinned `.standards-runner/` checkout over an npx-from-git wrapper but not yet tested in askit's exact setup; (3) whether to run all three PRs in sequence or test PR-A first against a throwaway caller before wiring askit for real, a step the plan's own confidence table flags as its only Medium-confidence, needs-a-live-run item, but which does not appear as an executable step in the plan's numbered task list.

### Sequencing invariants across all phases

Four invariants apply to every phase, not just Phase 0: no clause is ratified without a named enforcing check or an explicit aspirational label; no clause is ratified from a non-conforming exemplar; the three scarce numbers, the Standard version, the ADR number, and the section number, are allocated only at LAND on the protected branch, never reserved in a draft; and one version bump plus one ADR per landing is invariant, LAND is a single atomic PR of clause text plus a version bump plus one ADR plus a changelog entry. `GOVERNANCE.md`'s own amendment lifecycle runs five stages: EXPAND (a draft in `_local/`), PROPOSE (a land-ready draft or a formal RFC), REVIEW (a section-collision check), LAND (the atomic PR), RE-ADOPT (each plugin bumps its own `library.json` pin, on its own cadence).

## 3. Ranked risks and drift

1. **Execution is stalled at the maintainer authorization gate, roughly two weeks and counting.** PR-A (ship the org gate) has been the single named next action since 2026-06-20 and remains unauthorized as of this audit. Verified: no workflow file exists in `agent-plugins` or in `product-on-purpose/.github`; every phase downstream, relocation, pm-skills' `library.json`, the CI keystone, Section 14, Codex, is sequenced behind it. This is the dominant risk: all other work is blocked, and the plan's freshness decays daily.

2. **`GOVERNANCE.md`'s serialization mechanism is not actually configured.** Section 6 claims "branch protection requiring up-to-date-before-merge enforces the serialization mechanically," but live protection is `strict:false`. Two concurrent Standard amendments could collide on the next version/ADR/section number with no forced rebase. This is the clearest docs-vs-reality gap in the repo and directly undermines the allocation-at-land discipline the whole package relies on. `enforce_admins:false` compounds it: the solo maintainer can bypass all gates.

3. **pm-skills' two P0 conformance holes persist across three releases.** No `library.json` (cannot pin any Standard, fails listing clause L3), and a retained embedded self-listing `marketplace.json` (fails L2). Flagged 2026-06-10; v2.28.0, v2.29.0, and v2.29.1 all shipped since without touching either. pm-skills runs a fully proprietary roughly 40-script validator and never invokes the toolkit's `check.mjs`.

4. **thinking-framework-skills' "Gold" claim is not backed by its CI.** It pins Standard 0.8, now four minors behind 0.12 (one worse than the "three minors behind" characterization still recorded in memory), and its conformance gate checks out the toolkit at ref `2f480d1` from 2026-06-01, roughly 67 commits and several Standard minors stale. Its CI predates roughly half the Gold check suite and all of U13 (the skill-registration check). The self-declared Gold tier is currently unverified against the live Standard.

5. **writing-style-catalog has the largest pin-to-working-tree drift and an undocumented shipped skill.** Working tree is 0.6.0, 12 or more commits past the 0.5.2 pin, with a fully built, registered `entry-recommender` skill that has no `[0.6.0]` CHANGELOG entry and no session-log coverage across 21 commits and 3 releases. A fresh clone's changelog would not mention an entire shipped capability. This repo also has live concurrent agent activity: a commit landed mid-audit, and the `entry-recommender` proposal (PR #92) merged the same day as this audit.

6. **Two live roadmaps remain unreconciled (OQ-7, program-roadmap.md vs standards-plan-roadmap reconciliation).** `program-roadmap.md` and the standards-plan-roadmap package are both committed, mutually addressable, and neither is marked superseded, despite the newer package's explicit instruction to reconcile. They already disagree on Standard version (0.11 vs 0.12), registry version snapshots, orchestration epics (E1-E5 vs campaigns C1-C5), and Section 14 urgency. ## 5. Gaps the planning suite must cover

The existing standards-plan-roadmap package is a roadmap plus staged clause drafts plus one implementation plan, for Phase 0 only. A full PRD, spec, implementation, execution, CI, and release-plan suite must add what the package does not:

- **A PRD tying the program to outcomes and success metrics.** The package is decision- and phase-structured, not outcome-mapped. `program-roadmap.md`'s outcome framing (governance, sites, and orchestration mapped to outcomes) is exactly what the package dropped; the suite should absorb it or explicitly scope it out. Reconciling the two roadmaps (OQ-7) must be an explicit first step, not an assumption.
- **Implementation and execution plans for Phases 1 through 5.** Only Phase 0 has one. Phases 1 through 5 have clause drafts and campaign briefs but no executable, verify-gated plan of the Phase 0 caliber. pm-skills convergence (Phase 1, close P0 holes) in particular needs its own repo-local spec: the roughly 95-component manifest tooling, and the L2/L3 fixes.
- **A resolution pass over draft drift before drafts become specs.** The suite must fix, not inherit: the D8 (release subsystem) PLAN-layer phase, Phase 3, not 5, the missing D16 (HISTORY.md, amend and grandfather) amendment text, the stale pre-D17 Codex clause in the listing-contract edit, the D10 (cross-tool / truth-in-targeting) clause-landing-vs-enforcement phase conflation, and the pseudocode syntax defect.
- **A governance-enforcement plan.** Nothing in the package addresses that `strict:false` breaks the serialization `GOVERNANCE.md` depends on. The suite needs a CI and configuration plan covering the `strict:true` flip, the `enforce_admins` question, and how allocation-at-land is protected without a second maintainer.
- **A CI and release plan grounded in a real live run.** The reusable-workflow two-checkout wiring has never executed end-to-end, the one Medium-confidence item in the Phase 0 plan. The suite must schedule a live-Actions validation, a throwaway-caller test the Phase 0 plan recommends but does not schedule as an executable step, and confirm `product-on-purpose/.github` exists before wiring depends on it.
- **A fleet-campaign pilot plan.** Phase 3's push campaigns (C1-C5) assume a validated orchestration capability that has never run. The suite should require a proven FC-0001 pilot before the larger campaigns fan out.
- **Family drift monitoring as a shipped feature.** The pin-currency policy, the re-pin automation spec, and the registry `standard`/`tier` surfacing, all currently deferred, need to become tracked deliverables with acceptance criteria.
- **A Codex execution plan** that resolves the path-reconfirmation spike's build-time caveats (the install verb, `interface` object fields, `.mcp.json` shape, CLI version pin) rather than deferring them, and reconciles the naming hazard between the OpenAI Codex CLI and the `codex` Claude Code plugin.
- **Explicit "done" definitions and the dual-documentation contract** carried into every plan: kickoff-prompt shape, stop-and-flag on judgment changes, no-silent-skips, the PULL-vs-PUSH split, and the "no clause from a non-conforming exemplar, no clause without a named check" invariant.
- **Documentation-currency drift across the family**, which this audit surfaces repeatedly, pm-skills' dead `TODO.md`, writing-style-catalog's undocumented shipped skill, agent-skills-toolkit's stale memory index, is not addressed by any existing decision or draft. The suite should decide whether a documentation-currency convention or gate is in scope, or explicitly out of scope for this program.
- **A terminology disambiguation pass.** The package uses "tiered" for two different things: an option considered and rejected during OQ-1 (enforcement appetite), a permanent partial-blocking floor, and D15's actual chosen mechanism (enforcement, full tiered ramp), a temporary staged rollout toward full blocking of all three tiers. The suite's own execution language should not inherit this collision; an executor skimming only the word "tiered" could implement the wrong end state.
